# 语义与验证

## 指标契约与选型

| 问题 | 通常选择 | 必须明确 |
| --- | --- | --- |
| 发生多少次/累计多少量 | Counter | 尝试还是逻辑事件；记录入口还是结束；重启归零 |
| 现在有多少 | Gauge / 对应 OTel 状态仪表 | 本地还是全局；真实快照还是估算；数据年龄 |
| 延迟/大小分布 | Histogram | 单位、观察范围、桶/分辨率、跨实例聚合 |

这是概念映射，不是各 SDK 类型的一一映射。OTel 的同步/异步、UpDownCounter、temporality 和 Prometheus 的 Counter/Gauge/Histogram 需按实际数据模型选择。耗时使用秒等平台基础单位，不在同一时序混用单位。

最小设计记录：名称、用途、观测对象、类型/单位、数据来源、记录时机、结果分类、标签集合、重复/重试语义、新鲜度、消费者、负责人。尽量从现有实现填充，不必为微小变动另建文件。

例如：创建请求成功可包含幂等命中；真正新建任务数只在新对象提交成功后增加。请求完成次数不是请求到达次数，内部 retry 次数也不是外部请求数。

## 标签与时序预算

一条时序由指标身份和一组标签标识。同一组值在不同时间采到的点形成一条曲线。增加标签值会产生新组合，影响客户端聚合和后端存储。

- 优先 route template、有限结果分类、操作类别；不默认使用原始 URL、SQL、错误文本、request/user/task ID。
- 高基数不是绝对禁用：per-tenant SLO 等明确需求可以保留，前提是活跃集合、保留周期、预算和溢出语义经过评估。
- 组合上限近似各维度可能值数量相乘；实例数另外考虑，但不要重复计算已有实例维度。实际只有出现的组合存在，生命周期更替也影响后端历史基数。
- 经典 Histogram 每组通常展开为桶数（包含 +Inf）+ sum + count，客户端可能另有元数据时序。Native Histogram 不适用该展开公式，但样本大小与分辨率仍有成本。
- OTel SDK 基数上限保护本地聚合，不是全局后端上限。overflow 后总量与标签细分查询语义不同；不能宣称“设置 cap 后所有查询仍完整”。按使用版本确认实际行为。
- 已知有限分类可初始化 0；不要为了补 0 枚举全部高基数组合。

## 查询、告警与迁移

- 先对各 Counter 使用 rate/increase，再合并实例，保留重置检测。rate 不能恢复进程消失之前未被采到的所有事件。
- Gauge 的值不直接当 Counter 求请求速率；需要状态变化率时选择对应数学操作并说明用途。
- 比例的分子/分母要来自相同总体、时间窗、筛选条件和兼容的标签匹配；明确 canceled/invalid/timeout 是否算服务失败。
- 服务均值 = 总耗时增长 / 总观察数增长，不平均不同流量实例的均值。
- 服务 P99 = 合并分布后求分位数，不平均实例 P99；Summary 的预计算分位数不能这样聚合。
- 经典 Histogram 的桶是累计的，不直接把全部桶相加。聚合保留 le；Native Histogram 查询使用其适用形式。
- 区分无事件、零流量、采集失败、指标缺失、陈旧数据。缺数据不自动补 0 或显示绿色；零分母不能伪装成正常比例。
- HA 数据去重、全局快照重复导出和不同地区/服务的总体必须明确；不要把不相关系统混成一项健康比例。
- 告警阈值结合业务目标、最低流量、持续窗口、新鲜度和可行动性；不凭空复制统一阈值。
- 修改名称、标签、类型、单位、桶或记录边界前，搜索仪表盘、告警、recording rules、导出映射与依赖代码。混合旧新版本的过渡期要维持可解释查询；不要未经需要永久双写所有指标。

经典 Histogram 示例（需按实际环境添加筛选）：
```promql
sum(rate(task_create_requests_total[5m]))

sum(rate(task_create_requests_total{outcome="error"}[5m]))
/ sum(rate(task_create_requests_total[5m]))

sum(rate(task_create_duration_seconds_sum[5m]))
/ sum(rate(task_create_duration_seconds_count[5m]))

histogram_quantile(0.99,
  sum by (le) (rate(task_create_duration_seconds_bucket[5m])))
```

上面的 error 分类须已存在，5m 窗口仅作演示，应能覆盖足够采集点；不得直接当作所有项目的生产查询。

## 审查证据和验证选择

按影响报告 correctness、availability、成本问题。仅仅“有 SQL”“有标签”“有锁”不构成缺陷；指出实际执行条件、放大因素与影响。源码能证明风险机制，实际规模未知时应明确条件，不能把推算说成线上事故。

| 变化 | 优先验证 |
| --- | --- |
| 计数/记录边界 | 成功、异常、取消、幂等/重试；是否恰好记录预定事件 |
| Gauge | 退出清理、重启、本地/全局边界；是否漂移 |
| 标签/Histogram | 最大预期组合、内存、桶/单位；错误类别不会任意增长 |
| 查询/告警 | 多实例/重置、不等流量、零分母、缺失、陈旧、维度匹配 |
| SQL/快照 | 查询计划、规模、超时取消、并发抓取、首次失败和缓存过期 |
| 导出/缓冲 | 下游失联、慢响应、过载、重试/内存上限及关闭行为 |
| 兼容性改动 | 旧新消费者、混合版本窗口、重复统计和回滚 |

尽量复用现有测试工具与代表性样本。不要给低影响文档/计数器改动强加全套压力测试；没有授权不要为了验证主动冲击生产数据库。没有运行测试时明确说未运行，不能用 lint 通过宣称性能已验证。
