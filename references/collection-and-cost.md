# 采集与成本

## 热路径

- 利用当前返回值、错误类别或已有上下文；不为补标签查询用户/任务/数据库详情。
- 关注标签构造、时间读取、分配与竞争；高频处可缓存有限标签句柄、复用注册对象。只有测量证明必要时再优化，别为省一次 inc 牺牲关键错误可见性。
- 本地 Add/Observe 通常已经聚合，不要再套一个异步任务。SDK 是否会阻塞或访问网络须依据实际实现确认。
- 记录耗时用单调时钟，导出明确单位；最近成功时间用 Unix 时间值。两者不混用。
- Metrics 不是审计账本。事务已提交而进程在计数前崩溃，或增量在采集前丢失，均可能漏记。不要用同步等待遥测确认“修复”精确账务需求。

## 数据库和远程采集

从已有统计开始，不默认新建查询、缓存表、事件流或数据库写入。

必须查询时，确认：目标库与范围、查询计划/扫描规模、周期、执行实例数、HA 抓取副本、超时、连接/并发上限、重复采集方式、允许的数据延迟和关闭机制。

- COUNT(*)、只读和“有索引”都不是低成本证明。结合引擎、过滤条件、数据量与实际执行证据评估。
- 客户端超时不等于数据库停止工作。检查 context 取消传播及服务端 statement timeout 或等效限制。
- 避免全表扫描、N+1 补查询、锁定读取、轮次重叠及失败密集重试。必要的批量扫描有明确上界并隔离执行。
- 对全局业务状态明确采集归属，避免每个 Pod 重复读同一份数据；结果查询也不得把同一全局快照 sum 多次。
- 数据库各实例的自身健康指标则应逐实例采集，不能用一个全局刷新器掩盖单实例故障。
- 只读副本仍有资源成本及复制延迟，不能用“改读副本”代替预算。

示例：3 条查询 × 20 个应用实例 × 2 个抓取副本 ÷ 15 秒 = 平均新增 8 QPS。该计算只表示调用频率；还要看每次成本和同步触发的峰值。已有缓存/共享刷新时不能再机械乘抓取副本数。

## 快照范式

适用于已确认昂贵、且允许延迟的状态查询，不是所有 exporter 的默认方案。

1. 受控刷新取得状态；超时、并发有限，避免轮次重叠。
2. 成功时原子更新数值及最近成功时间。
3. 失败时暴露失败状态，不把原值覆盖成 0，也不推进成功时间。
4. 从未成功时，省略未知数值或使用平台约定的明确无效状态；不伪造 0。
5. 采集读快照；消费者结合状态和年龄判断能否使用。

指标可为 `tasks_pending`、`tasks_pending_refresh_success`、`tasks_pending_last_success_timestamp_seconds`。用当前时间减成功时间计算年龄；陈旧数据不能因每次抓取带上新时间戳而被视为最新。若进程使用累计事件估算存量，必须说明重启恢复、跨实例与外部更新机制，否则只能称估算值。

## 故障隔离与过载

- 有限内存、队列、并发、重试次数/总时长与关闭超时；重试退避，周期可错峰。
- 不使用业务请求生命周期之外无界存活的后台任务。
- 遥测异常不能覆盖原返回值或业务异常；也不应吞掉业务错误以“保证埋点成功”。
- 过载可按 SDK 支持的明确策略丢弃遥测，并暴露丢弃/溢出/失败；诊断日志也要限频。
- 不随意采样 Counter 后仍把它称为完整总量。改变采样必须说明估算方式、误差和消费者影响。
- 验证下游不可用、慢响应、最大预期标签集和并发抓取时业务仍可完成、资源不持续无界增长。
